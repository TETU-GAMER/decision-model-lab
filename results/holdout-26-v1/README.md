# 26% 的澄清分界线在新工单上表现如何？

简体中文 | [English](README.en.md)

模型对 24 条新工单发起了 11 次追问。按审核者事先给出的标签，这 11 条都可以直接分给部门。真正需要追问的 3 条全部被直接分走。模型最终答对 8/24 条（33.3%）。

## 和开发集用同一条分界线对比

- **该追问时能否认出来？** 开发集认出 5/6 条（83.3%），新工单认出 0/3 条（0%）。这 3 条都要求同时处理两个涉及不同部门的问题，其中 1 条被分给技术支持，2 条被分给配送。
- **能直接分的工单有多少被多问？** 开发集是 3/18 条（16.7%），新工单是 11/21 条（52.4%）。其中包括全部 6 条审核为配送的工单。其余 10 条可分单工单中，8 条分对部门，2 条分错。

同一个设置在开发集上共答对 19/24 条。26% 是在查看开发集标签后选出的。这批新工单只有 3 条审核为需要澄清，尚不足以估计真实客服工单的漏判率。 [开发集分数对照](../clarification-thresholds-v1/README.md)

## 两条工单的去向

一位客户想知道用礼品卡和借记卡付款后，退一件商品的钱会退到哪里。澄清分数为 26.09%，刚过分界线，模型就追问了。另一位客户要求同时补充快递房号和核对上月应到账的抵扣额。澄清分数只有 17.78%，模型把两个问题一起交给了配送。 [逐条模型响应](predictions.jsonl)

## 实验设置

24 条工单均为新编的合成文本。审核者每次看三条，在模型运行前完成全部分类。推理使用英文原文和固定版本的原模型权重，全程没有微调。“直接分单”排在第一位，澄清分数达到 26% 就结束分单并追问，低于 26% 才选部门。24 次第一步调用和 13 次选部门调用均成功。 [预先固定的设置](../../data/holdout_protocol_v1.json) · [两步提示词](prompts.json)

在仓库根目录准备好固定版本的模型及本机审核记录后，运行 `python -X utf8 -m experiments.two_stage_routing --holdout`。使用不同的审核标签会改变评分。 [分数与混淆矩阵](scores.json) · [版本和运行环境](metadata.json)

## 只加一句“先查抵扣额”

对“快递需要房号，上月的抵扣额也没到账”这条工单，又做了一次单条对照。两版都保留原文最后的“两件事都希望今天处理”。第二版只在末尾加了一句 `Please check the missing credit first.`。两版都用原模型权重和同一个 26% 分界线，各自重新运行。

- **原文**应先追问。澄清分数为 17.78%，模型直接分单，选了配送。两步的模型响应都复现了上一轮的结果。
- **加一句后**应交给账单。澄清分数为 21.90%，仍然直接分单。第二步里，账单的分数由 13.46% 升到 19.05%，配送由 74.00% 降到 68.82%，最终还是去了配送。

模型在这对输入上两次都选错了。原文错在第一步该不该追问，加句版错在第二步该选哪个部门。复现命令为 `python -X utf8 -m experiments.priority_pair`。 [两版原文与完整模型响应](priority-pair.json)

## 把“先查抵扣额”移到开头

两版都明确要求先查抵扣额，都应分给账单。这次只移动了整句 `Please check the missing credit first.`，保留其余文字、标点和先后顺序。两版各跑了一次，使用相同的模型权重、提示词、候选顺序和 26% 分界线。

- **放在末尾**时，澄清分数为 21.90%。选部门时，账单为 19.05%，配送为 68.82%，最终选了配送。此次重跑复现了上次末尾版的两步响应。
- **移到开头**后，澄清分数为 19.48%。选部门时，账单升到 21.00%，配送也升到 69.88%，最终仍选配送。

对这条工单，把优先事项提前没有纠正分单。复现命令为 `python -X utf8 -m experiments.priority_pair --compare-position`。 [句子位置对照的原文与响应](priority-position.json)

## 去掉补房号，只留查抵扣额

沿用刚才把优先要求放在开头的版本。删掉快递需要房号的部分，把结尾的“两件事”改成“这件事”，保留“今天处理”。模型实际读到的单问题版本是：

> Please check the missing credit first. Last month's credit is missing from my balance. I'd like this sorted out today.

- **两个问题一起提。** 澄清分数为 19.48%，模型继续选部门，账单得分 21.00%，配送得分 69.88%，最终去了配送。两步响应均复现了上一轮的开头版。
- **只提抵扣额。** 澄清分数升到 26.81%，超过固定的 26% 分界线。正式分单流程在第一步就选了“需要澄清”。

为查明第二步会怎样处理这条单问题工单，我们把同一段英文单独交给原来的选部门步骤。它选了账单（50.59%），配送为 28.70%，技术支持为 20.70%。因此，这个样例在正式流程中被第一步拦下。两版的正式分单在复跑时给出了相同响应，全程使用原模型权重。复现命令为 `python -X utf8 -m experiments.priority_pair --compare-credit-only`。 [两版分单与单独选部门的记录](credit-only.json)
